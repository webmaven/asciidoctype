= AsciiDoctype Architecture
:toc: left
:toc-title: Contents
:toclevels: 4
:icons: font
:source-highlighter: highlight.js

This document describes the internal design, rendering pipeline, template
resolution strategy, and ASG node coverage of AsciiDoctype.

== 1. System Position in the Ecosystem

AsciiDoctype occupies the **formatting layer** between a semantic document
parser and an output orchestrator:

....
┌─────────────────────┐
│  Author (*.adoc)    │
└──────────┬──────────┘
           │  raw AsciiDoc text
           ▼
┌─────────────────────┐
│   AsciiDoctrine     │  Parser + TCK-compliant semantic graph
│  (ASG producer)     │
└──────────┬──────────┘
           │  Python dict (via to_dict())
           ▼
┌─────────────────────┐
│   AsciiDoctype      │  ← THIS LIBRARY
│ (Template renderer) │  Chameleon ZPT templates → HTML5 or XHTML strings
└──────────┬──────────┘
           │  markup string fragments / full document string
           ▼
┌──────────────────────────────┐
│  Golem SSG / EPUB Compiler / │  Orchestrator: writes files, manages assets
│  Custom downstream tool      │
└──────────────────────────────┘
....

**Key invariant:** AsciiDoctype never reads from disk (beyond template lookup),
never writes to disk, and never modifies the ASG nodes it receives. It is a
pure in-memory transformation — dict in, string out.

== 2. Core Components

=== 2.1 `AsciiDoctypeRenderer`

The single public class. Constructed once per rendering session (or once per
target format) and reused across many `render()` calls.

[source,python]
----
renderer = AsciiDoctypeRenderer(
    target_format="html5",        # or "xhtml"
    search_paths=[Path("theme/")], # optional, ordered
)
----

**Responsibilities:**

* Validate `target_format` and raise `ValueError` on bad values.
* Build the ordered search path list, appending the bundled core fallback last.
* Initialise a `chameleon.PageTemplateLoader` over the resolved paths.
* Dispatch each incoming ASG node dict to the correct template via `render()`.
* Wrap any template runtime error in `AsciiDoctypeRenderingError` for clean
  diagnostics.

=== 2.2 `AsciiDoctypeRenderingError`

A typed sentinel exception that carries the failing node name, the target
pipeline, and the root cause. Callers can catch this to implement graceful
degradation without catching every possible Python exception.

=== 2.3 Chameleon `PageTemplateLoader`

Manages the compiled-bytecode template cache. Templates are compiled to Python
bytecode on first use; subsequent calls reuse the cache. This gives near-native
rendering speed even for large, deeply-nested documents.

== 3. Template Resolution Pipeline

Template lookup follows a strict precedence order at every `render()` call:

....
Caller search_paths[0]   →  search_paths[1]  →  …  →  core_templates/<fmt>/
(user overrides)            (active theme)          (bundled fallback)
....

The algorithm:

1. Compute `node["name"]` (e.g. `"paragraph"`).
2. Call `self.loader["paragraph.html"]`.
3. Chameleon's `PageTemplateLoader` searches its path list in order and returns
   the first match.
4. If no match is found anywhere, `ValueError` is caught internally and
   `fallback_container.html` is used instead.
5. The resolved template is executed with `(node=node, renderer=self, ctx=ctx)`.

This means a theme can override any single template file without providing all
of them — missing overrides silently fall back to the bundled core.

=== 3.1 Template Variables Available in Every Template

[cols="1,1,3",options="header"]
|===
|Variable |Type |Description

|`node`
|`dict`
|The current ASG node dictionary being rendered. Shape varies by node type
(see <<asg-node-schemas>>).

|`renderer`
|`AsciiDoctypeRenderer`
|The renderer instance. Used to call `renderer.render(child, ctx)` for
recursive child rendering.

|`ctx`
|`dict`
|Arbitrary caller-supplied context (e.g. site settings, base URL). Empty dict
if not provided. Templates may read from it but must not mutate it.
|===

=== 3.2 Recursive Child Rendering in Templates

All child node lists are rendered by calling back into the renderer from inside
the template. The `structure` modifier is **mandatory** to prevent Chameleon
from HTML-escaping the returned markup string:

[source,xml]
----
<tal:block tal:repeat="inline node.get('inlines', [])"
           tal:replace="structure renderer.render(inline, ctx)" />
----

Without `structure`, child tags would appear as literal escaped text
(`&lt;strong&gt;`) instead of live markup.

== 4. Dual Rendering Pipelines

=== 4.1 HTML5 Pipeline

Target: modern browsers, progressive web apps.

* Void elements have no closing slash (`<br>`, `<img>`, `<meta>`).
* Document opens with `<!DOCTYPE html>`.
* No XML declaration or namespace binding.

=== 4.2 XHTML 1.0 Strict Pipeline

Target: EPUB 2/3 readers, Kindle, strict XML parsers.

* XML declaration: `<?xml version="1.0" encoding="UTF-8"?>`
* DOCTYPE: `<!DOCTYPE html PUBLIC "-//W3C//DTD XHTML 1.0 Strict//EN" …>`
* Root namespace: `<html xmlns="http://www.w3.org/1999/xhtml">`
* `<meta http-equiv="Content-Type" content="text/html; charset=UTF-8" />`
* All void elements explicitly self-closed.

== [[asg-node-schemas]]5. ASG Node Schemas and Template Coverage

All nodes are Python dicts produced by AsciiDoctrine's `to_dict()` method.
AsciiDoctype receives them as plain dictionaries — it has no knowledge of any
class hierarchy.

=== 5.3 Fallback Container

Any node whose `name` has no corresponding `<name>.html` template is rendered
via `fallback_container.html`. It wraps the node's `blocks` or `inlines`
children in a `<div class="adoc-fallback node-<name>">` element, preserving
recursive rendering while clearly marking unsupported nodes in the output.

== 7. Design Constraints

* **No file I/O in production code.** AsciiDoctype only reads template files;
  it never writes anything to disk.
* **No state mutation.** The `ctx` dict and `node` dicts passed to `render()`
  are treated as read-only.
* **O(N) rendering complexity.** Cost scales linearly with the number of nodes
  in the document tree.
* **No styling.** AsciiDoctype emits clean semantic markup. CSS, fonts, and
  design tokens are downstream concerns.
* **Python 3.9+.** Uses `dict` type hints without `typing.Dict` for conciseness.
  Must remain compatible with CPython 3.9 through current.

== 8. Downstream Extension Points

Downstream systems (Golem SSG, EPUB compilers, etc.) can extend the rendering
pipeline without modifying AsciiDoctype:

=== 8.1 Custom Templates via `search_paths`

The most common pattern: provide a theme directory with custom `.html` template
files. The templates receive the same `node`, `renderer`, and `ctx` variables.

=== 8.2 Custom ASG Nodes

A Golem plugin may inject additional node types into the ASG (e.g. a Mermaid
diagram node named `"mermaid"`). As long as the theme provides `mermaid.html`,
AsciiDoctype will render it without modification. No core code change required.

=== 8.3 CSS Classes and IDs

Templates may emit arbitrary CSS classes and `id` attributes to allow
downstream styling without AsciiDoctype carrying any style responsibility.
For example, a theme's `section.html` might add `data-` attributes for
JavaScript-driven interactive features.

=== 8.4 Context Dictionary

The `ctx` dict flows through every recursive call. A Golem orchestrator might
populate it with site-level settings (`base_url`, `locale`, navigation data)
that templates can read to produce context-aware output.
